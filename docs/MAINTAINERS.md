# Maintenance and publishing policy

This is a personal creative hobby with professional engineering standards and a long-term ambitious vision. The owner makes creative direction, account, spending and permission decisions; routine documentation, tests, issue triage, attribution checks and implementation details should be automated or handled through reviewable changes wherever possible.

## Release and maintenance gates
- Never claim a feature exists before code and tests demonstrate it.
- Document material architectural decisions as ADRs.
- Track third-party source, version, license, modifications and obligations before import.
- Require tests for deterministic simulation and replay.
- Prefer small reviewed changes and automated validation.
- Do not promise ongoing background work, unattended publishing or monitoring unless an actual scheduled workflow is configured.
- Ask owner approval for paid services, sensitive account actions, license exceptions and major creative changes.

## Public status
The README distinguishes planned vision from implemented milestones. Avoid unsupported scale/performance claims.
